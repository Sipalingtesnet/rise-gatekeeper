# rise — Proof Gatekeeper agent

**rise** is an AI-agent entry for the **Proof Gatekeeper** track of
[zkVerify Agent Games, Season 01](https://agentgames.zkverify.io) (21 Oct –
21 Nov 2026). It is a small Node.js service that answers incoming
gatekeeper tasks with an `APPROVE` / `REJECT` decision, following the real
agent interface from the Games' Playbook (§02 "Agent Interface — Receive,
decide, respond"), and — when configured — generates a real Groth16 proof
of each decision with snarkjs and submits it to zkVerify via Kurier (see
[Proofs](#proofs)).

## The game

In Proof Gatekeeper the arena sends the agent incoming tasks — proof-backed
payment requests — and the agent must decide whether to approve them. The
decision boundary is strict:

> **APPROVE only when every field agrees. Anything else is a REJECT.**

| Reason | Meaning |
|---|---|
| `VALID_CONDITION` | Everything agrees → **APPROVE** |
| `VK_SUBSTITUTION` | `proof_vk` differs from `registered_vk` → **REJECT** |
| `RECIPIENT_MISMATCH` | `recipient` differs from `condition_recipient` → **REJECT** |
| `THRESHOLD_MISMATCH` | A threshold check fails (amount / balance / expiry / deadline) → **REJECT** |

`rise` implements exactly that boundary, and it **fails closed**: missing
reference values, a stale deadline, any error, or any uncertainty is a
REJECT — never an approve by default.

## API

### `GET /health`

Health check for the arena (unsigned liveness check).

```json
{ "status": "ok", "agent": "rise" }
```

### `POST /agent` — authenticated

Every request must carry a valid `x-agent-games-signature` header: HMAC-SHA256
over the **raw request body**, keyed with the agent secret (see
[Secret](#secret) below). The signature is verified against the raw body
**before** any parsing. A bad or missing signature gets HTTP 401 and no
decision. Every response is signed the same way (HMAC over the raw response
body, same header, same secret).

#### Incoming task envelope — Proof Gatekeeper

```json
{
  "type": "agent-games.proof-gatekeeper.v1",
  "task_id": "gk_8d31...",
  "mode": "competition",
  "issued_at": "<issued-at>",
  "deadline_at": "<deadline>",
  "input": {
    "registered_vk": "0x7d...01",
    "proof_vk": "0x13...aa",
    "minimum": "1000",
    "public_balance": "1460",
    "expiry_block": 8430000,
    "current_block": 8420000,
    "recipient": "0xDe62..9F81",
    "condition_recipient": "0xDe62..9F81",
    "amount": "500",
    "max_transfer": "1000",
    "proof_tx": "0xa8...2c"
  }
}
```

Checks, in order:

1. **Proof VK** — `proof_vk` must match `registered_vk` exactly (hex,
   case-insensitive). Missing either side → `VK_SUBSTITUTION`.
2. **Recipient** — `recipient` must match `condition_recipient`
   (case-insensitive). Missing either side → `RECIPIENT_MISMATCH`.
3. **Thresholds** — all must hold, otherwise `THRESHOLD_MISMATCH`:
   - `amount` is a non-negative number and `amount <= max_transfer`;
   - `public_balance >= minimum`;
   - `current_block <= expiry_block`.
   Integer values are compared with `BigInt`, so large on-chain values do
   not lose precision. A missing or non-numeric reference fails closed.
4. **Deadline** — when `deadline_at` is present and parseable (ISO 8601 or
   epoch seconds/milliseconds), a task past its deadline is stale →
   `THRESHOLD_MISMATCH`. This is the Playbook's 60s hard deadline; the HTTP
   server additionally closes requests still open after 60s.

#### Required response (200, `application/json`)

```json
{ "decision": "REJECT", "reason_code": "VK_SUBSTITUTION", "proof_tx": "0xa8...2c" }
```

`proof_tx` is echoed from the task's `input.proof_tx` when present. When a
real proof exists, `proof` and `public_signals` are included too (see
[Proofs](#proofs)); until then they are omitted.

#### Preflight — runs before any task

After registration and rotating the secret, the platform sends a signed
preflight request to verify the endpoint can authenticate and sign
responses. It is dispatched on `type`, never treated as a task:

```json
{ "type": "agent-games.preflight.v1", "agent_id": "ag1_...", "issued_at": "<issued-at>", "nonce": "abc123" }
```

Response (signed):

```json
{ "ok": true, "protocolVersion": "v1" }
```

Preflight must pass before the platform marks the agent active.

#### Errors

| Status | Meaning |
|---|---|
| 401 | Missing/invalid signature, or no secret configured on the server |
| 400 | Malformed JSON, non-object body, or unknown message `type` |
| 404 | Unknown path |

## Secret

The HMAC secret is generated by the platform and revealed **once** via
"Rotate Secret" on the dashboard. The operator copies the plaintext and sets
it as `AGENT_GAMES_HMAC_SECRET` in the environment. It is never hardcoded,
never committed, and never logged. Without it, `POST /agent` refuses
everything (fail closed). `.env` is git-ignored; copy `.env.example` to
`.env` and fill it in.

## Proofs

The Playbook calls for local Groth16 proof generation with snarkjs (using
the downloaded wasm/zkey) and zkVerify submission via Kurier REST, waiting
for a finalized result before treating a proof as confirmed. That flow is
implemented for real in [`proof.js`](proof.js) —
`generateProof()` → `submitProof()` → poll to `Finalized` — and the
circuit artifacts ship in [`circuits/`](circuits/) (see
[`circuits/README.md`](circuits/README.md) for provenance and hashes).

**Circuit.** Groth16 / BN128, Circom 2.x, template `GatekeeperEvaluation`
(13 input signals, 13 public signals). Registered verification-key hash on
zkVerify mainnet (from `https://agentgames.zkverify.io/api/circuit-info`):

```
0x6b79c6012a6d8651f3e13bc4d2a20370280ab49700c90c5316d4168bfbad77b0
```

**Circuit inputs — discovered empirically, not published on the Playbook.**
The 13 input signal names were found by probing the downloaded wasm with
circom_runtime's witness calculator (a name that exists is accepted; any
other name errors), and the encodings were confirmed by generating proofs
and verifying them locally against the exported verification key. The
mapping lives in ONE function, `buildCircuitInputs()` in `proof.js`:

| Signal | Encoding |
|---|---|
| `recipient`, `conditionRecipient` | `BigInt(0x-address)` (160-bit fits the field) |
| `amount`, `maxTransfer`, `minimum`, `publicBalance`, `expiryBlock`, `currentBlock` | `BigInt` as-is |
| `decision` | `1n` for APPROVE, `0n` for REJECT |
| `taskId` | `keccak256(utf8(taskId)) mod p` |
| `registeredVkHash`, `proofVkHash` | `BigInt(0x-hash) mod p` (256-bit hash exceeds the field modulus) |
| `salt` | `keccak256('agent-games-salt\|' + taskId) mod p` — deterministic per task |

**Public signals (13, in order):**

```
[ Poseidon(salt, taskId), registeredVkHash, proofVkHash, minimum,
  publicBalance, expiryBlock, currentBlock, recipient,
  conditionRecipient, amount, maxTransfer, decision, taskId ]
```

Public signal 0 — `Poseidon(salt, taskId)` — is the proof reference
(nullifier) binding the proof to its task; it was identified by varying
one input at a time and matching the value against Poseidon candidates.
The circuit enforces decision correctness: a decision inconsistent with
the checks fails witness generation (assert in the template), so only the
decision `decide.js` already computed is ever proven — the circuit is the
referee.

**Kurier flow (Playbook §03, RECOMMENDED; zkVerifyJS is not implemented).**

```js
POST https://api.kurier.xyz/api/v1/submit-proof/{KURIER_API_KEY}
{ proofType: 'groth16', vkRegistered: true,
  proofOptions: { library: 'snarkjs', curve: 'bn128' },
  proofData: { proof, publicSignals, vk: GATEKEEPER_VK_HASH } }

GET https://api.kurier.xyz/api/v1/job-status/{KURIER_API_KEY}/{jobId}
// states: Submitted → IncludedInBlock → Finalized (only Finalized counts)
```

**To go live** (the operator — a Kurier API key needs the operator's
account, it cannot be created by the agent):

1. Create a Kurier mainnet API key at https://kurier.xyz and set
   `KURIER_API_KEY` (see `.env.example`). The key goes in the Kurier
   request path, never in a header, never in logs.
2. Set `PROOF_ENABLED=1` so the server attempts proof generation. The
   attempt is capped at 45s (local proving is ~1s; Kurier submit + polling
   to Finalized takes the rest) — well inside the Playbook's 60s hard
   deadline. A failure or timeout simply omits the `proof` /
   `public_signals` fields and never changes the decision.

Without `PROOF_ENABLED=1` or without a Kurier key, the decision path works
fully on its own and the proof fields stay omitted.

## Run locally

Requires Node.js 22.3+ (`--test-force-exit` in the test script needs it;
snarkjs's worker threads otherwise keep the test runner alive after the
tests finish — see `package.json`).

```bash
npm install          # snarkjs + js-sha3 (proofs); circomlibjs is dev-only (tests)
cp .env.example .env   # set AGENT_GAMES_HMAC_SECRET to a test value
node server.js         # listens on :3000 (or $PORT)
```

Try it (sign requests with the same secret):

```bash
curl -s localhost:3000/health

BODY='{"type":"agent-games.proof-gatekeeper.v1","task_id":"gk_901","deadline_at":"2999-01-01T00:00:00Z","input":{"registered_vk":"0x7d01","proof_vk":"0x7d01","minimum":"1000","public_balance":"1460","expiry_block":8430000,"current_block":8420000,"recipient":"0xDe629F81","condition_recipient":"0xde629f81","amount":"500","max_transfer":"1000","proof_tx":"0xa82c"}}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$AGENT_GAMES_HMAC_SECRET" | cut -d' ' -f2)
curl -s -X POST localhost:3000/agent -H 'content-type: application/json' -H "x-agent-games-signature: $SIG" -d "$BODY"
```

## Tests

```bash
npm test        # node --test --test-force-exit test.js — 36 tests, 0 fail
```

(`--test-force-exit` is needed because snarkjs's worker threads keep the
test process alive after the tests finish; it requires Node 22.3+.)

The suite covers the pure decision logic on the real nested schema (approve
on a fully valid task, reject on each mismatch kind, balance/expiry/deadline
failures, fail-closed on missing references, boundary and BigInt cases), the
HMAC helpers (round-trip, wrong secret, tampered body, `sha256=` prefix),
the proof module — real local proof generation (approve-case and
reject-case proofs verify against the exported verification key, public
signals match the documented layout including `Poseidon(salt, taskId)` as
signal 0, an inconsistent decision fails proof generation) and Kurier
submission against a stubbed fetch (Finalized flow, missing key, failed
submit, no network in tests) — and live HTTP tests of the spawned server:
signed task → signed `APPROVE`, signed tampered task → signed `REJECT`,
signed preflight → signed `{ok:true, protocolVersion:"v1"}`, missing/bad
HMAC → 401 with no decision, malformed JSON (valid signature) → 400,
unknown type → 400, stale task → `REJECT`, and a server with no secret
refusing every POST.

## Deploy as a service

The Agent Games registration form takes an optional agent endpoint, e.g.
`https://my-agent.fly.dev/agent`. One way to host this service is
[fly.io](https://fly.io):

```bash
fly launch --no-deploy   # answer the prompts, pick a region
fly secrets set AGENT_GAMES_HMAC_SECRET='<paste the dashboard secret>'
fly deploy
fly open                 # check https://<app>.fly.dev/health
```

Then register the endpoint URL (`https://<app>.fly.dev/agent`) in the
Agent Games dashboard. Any other Node host works the same way — the service
only needs `node server.js`, the `AGENT_GAMES_HMAC_SECRET` env var, and a
public URL.

> **Fly.io pricing warning (checked 2026-11-14):** new organizations have
> NO free tier. A new account gets a trial only ($1 credit / 2 machine-hours
> / 7 days, no card to start) and **trial machines stop after 5 minutes of
> running** — unusable for an always-on agent that must answer tasks and
> health checks at any time. After the trial, the cheapest always-on machine
> costs ~$2/month and a credit card is required. Do not deploy to fly.io on
> the trial expecting it to stay up.

## Deploy on Vercel (free, no card)

The same agent is also packaged as Vercel serverless functions
(`api/agent.js` → `POST /api/agent`, `api/health.js` → `GET /api/health`),
so it runs on the Vercel Hobby plan: $0, no credit card, no sleep — a
serverless function is always available and answers in well under the
10s Hobby limit (the decision itself is pure computation, milliseconds).

```bash
npm i -g vercel        # or use the Vercel dashboard: import this repo
vercel login           # authorize with GitHub
vercel deploy          # note the https://<app>.vercel.app URL
vercel env add AGENT_GAMES_HMAC_SECRET production   # paste the dashboard secret
vercel deploy --prod
curl -s https://<app>.vercel.app/api/health
```

Then register the endpoint URL (`https://<app>.vercel.app/api/agent`) in
the Agent Games dashboard. The adapter mirrors `server.js` exactly (HMAC
verify before parsing, preflight, signed responses, fail-closed without a
secret) — the one deliberate difference is that **no proof generation is
attempted here**: the 10s Hobby limit does not fit snarkjs/wasm proof
generation plus Kurier polling to Finalized (the server path budgets 45s),
and `PROOF_ENABLED` is ignored. Decisions are always returned;
`proof` / `public_signals` stay omitted on the serverless path. If live
proofs are needed, deploy `server.js` on a real host instead (see fly.io
above) and set `PROOF_ENABLED=1` with a Kurier API key.

## Assumptions

The Playbook documents the envelope, the decision boundary, the preflight,
and the secret flow, but leaves these details unspecified — each was resolved
as follows (all documented in code where it matters):

1. **HMAC wire format**: the header carries lowercase hex HMAC-SHA256 of the
   raw body. A `sha256=<hex>` prefixed value is also accepted on verify.
   (If the platform uses a different construction — e.g. HMAC over
   `timestamp + "." + body` — only `hmac.js` needs to change.)
2. **Response shape**: exactly `{decision, reason_code, proof_tx?}` plus
   `proof` / `public_signals` when a proof exists. The v1 `reason` /
   `agent` / `taskId` fields were dropped to match the Playbook.
3. **`minimum` check**: `public_balance >= minimum` (the minimum required
   balance), derived from the field names. `amount` is checked against
   `max_transfer` only.
4. **Block expiry**: `current_block <= expiry_block` → valid; past it →
   `THRESHOLD_MISMATCH`.
5. **Deadline**: `deadline_at` accepts ISO 8601 or epoch seconds /
   milliseconds. An unparseable `deadline_at` is ignored (metadata, not a
   decision field); an absent one is not checked.
6. **Preflight**: dispatched on `type` only; the `nonce` is not replay-checked
   (no replay store is specified) — authentication rests on the HMAC.
7. **Proof encodings**: the Playbook does not publish the circuit's input
   signal names or their encodings. The names were discovered by probing
   the downloaded wasm, and the encodings (keccak256-mod-p for `taskId`
   and the VK hashes; deterministic per-task salt) were confirmed by
   generating proofs and verifying them locally against the exported
   verification key (see [Proofs](#proofs)). The vk_hash used for Kurier
   is the live value from `/api/circuit-info` (screenshot transcriptions
   of the hash were truncated by OCR and are not authoritative); its
   construction from the verification key was not reproduced, so the
   published constant is used as-is. The salt is deterministic per taskId
   rather than random — the platform only ever sees `Poseidon(salt,
   taskId)`, which is unique per task.
8. **Task `mode`** (`competition` / `practice`) is accepted and ignored — the
   decision logic is identical for both.
